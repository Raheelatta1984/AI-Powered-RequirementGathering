# What changed from v12 to v13

v13 keeps the v12 workflow and evidence model intact, and changes how answers are developed, how stakeholders participate, and which processes are mandatory.

## 1. Answers are elicited into detailed statements

Each answered question now produces two records:

| Field | Meaning |
|---|---|
| `text` | The stakeholder's original answer, retained verbatim |
| `detail` | A detailed, testable restatement with the requirement focus, the reported position, the implication, and what still needs confirming |
| `detailGaps` | Explicit gaps: no baseline, no named owner, no evidence source, vague terms |
| `detailEngine` | `guided` (deterministic), `ai` (model rephrase), or `stakeholder-edited` |

The stakeholder sees the expanded version immediately and can refine the wording. Refinements are attributed and invalidate dependent review approvals. The handoff includes both the original and the detailed version; the detailed version is an expansion, never new evidence, and the guided/AI expansion is rejected if it introduces a number the stakeholder did not supply.

## 2. Suggestions and priorities

- Suggested answers are now detailed, question-specific starting points rather than short fragments.
- The arrow on a suggestion **submits that answer immediately**; the body of the card still fills the composer for editing.
- MoSCoW priority is **auto-adjusted from the question** (mandatory, regulatory, security, and core-workflow topics become `Must have`; parked scope becomes `Won't have this release`). The reason is displayed, the stakeholder can override it, and `prioritySource` records which happened.
- Requirement-level priority uses the strongest recorded priority rather than the most recent one.

## 3. Change management is optional

- Workspace **master setup** (`PUT /api/settings`) with a Prosci-informed master switch, three individually optional phases, five individually optional ADKAR outcomes, and an optional people-and-adoption review.
- New engagements copy the defaults; each engagement can override them (`PUT /api/engagements/:id/change-management`).
- When disabled, the delivery gate ignores sponsor, impact, ADKAR, and change review. When enabled, only the switched-on elements are enforced.
- Records migrated from v12 keep the mandatory gates they were reviewed against, so existing approvals remain meaningful.

## 4. Parallel stakeholders and live progress

- `POST /api/engagements/:id/stakeholders` invites a stakeholder at any time; their sittings can overlap with existing stakeholders so interviews run in parallel.
- Adding a stakeholder archives prepared verification checks and invalidates approvals, because the evidence set changed.
- The new **Live progress** tab shows, per stakeholder: question number, phase matrix, answered counts, current phase, last activity, pause/break state, time budget, and reminders sent.
- Stakeholders record **how much time they have** (`POST /interviews/:token/time-budget`). Pacing tells them what remains and offers a pause when the budget runs out.
- Presence heartbeats and pause/break state use a non-revision-bumping mutation, so an active interview cannot fail its version check.
- Reminders are in-app and attributed. Automatic reminders respect pause, break, completion, a cool-down, and a daily limit.

## 5. Changelog and What's new

- `CHANGELOG.md` records past releases, the present (`[Unreleased]`), and the future (`[Planned]`).
- The **What's new** tab renders it through `GET /api/changelog`.
- `.github/workflows/changelog.yml`, `scripts/check-changelog.mjs`, and the pull-request template require an entry with every pull request and merge.

## 6. Data migration

Workspace schema 12 is migrated in place to schema 13 on first start:

- `settings` gains the master setup.
- Each engagement gains `changeManagement` (legacy: fully enabled) and `interviewSettings`.
- Each stakeholder gains `timeBudget`, `startedAt`, `lastSeenAt`, `reminders`, and `activity`.
- Each response gains `detail`, `detailGaps`, `detailEngine`, and `prioritySource`.

Existing answers keep empty detail values until they are re-read; nothing is fabricated for historical responses. Back up `workspace.json` before upgrading.
